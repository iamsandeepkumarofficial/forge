What you see in the UI

The workbench has a collapsible panel at the bottom (Terminal / DevTools). The dock uses a vertical sidebar of tabs (resizable) plus an xterm pane:

Tab kind What it is Can you type? How it appears / how output arrives
shell A bash login shell inside tmux in your session sandbox Yes Always available; live PTY over session WebSocket
app Web app from Run / preview_start No — read-only Auto-subscribe — Run / preview_start tracks app:{name} on session WS; compose strip + dock; exited unsubscribes. No /tabs poll
job Agent background run_terminal No — read-only Auto-subscribe — chat background run_terminal tracks the job over session WS; compose strip lists it; dock tab opens from the strip. exited unsubscribes. No boot /jobs list

There is no Stop button on dock tabs (close still hides/unpins). Stop apps from the Run panel; stop background jobs with the agent’s run_terminal action=stop. Above the chat composer, a collapsed “N terminals running” strip lists tracked apps/jobs (socket lifecycle — no polling) and focuses that dock tab when clicked.

One WebSocket per workbench session multiplexes shell, app, and job streams: /internal/terminal/session?sessionId=…

The sandbox container and tmux

Each Forge chat session gets a dedicated Docker sandbox container (your workspace files are mounted at /workspace). Inside that container Forge runs tmux — a terminal multiplexer.

tmux session layout

  • Session name: forge
  • First window: main, running bash -l (created lazily on first use)
  • Extra shell tabs: new tmux windows, each with its own bash -l (names like sh-a1b2c3)

tmux keeps those shells alive even when you close the workbench tab or refresh the page. The shell is not tied to your browser connection — only the view into it is. 

# Created once per container (simplified)
tmux new-session -d -s forge -c /workspace -n main bash -l

# Each "+" shell tab in the UI
tmux new-window -t forge -n sh-a1b2c3 -c /workspace bash -l

What is a PTY?

A PTY (pseudo-terminal) is what makes bash behave like it is connected to a real keyboard and screen — colors, line editing, window size, prompts, and programs like vim or npm run dev in interactive mode.

Your browser (xterm.js) Forge server Docker sandbox ┌─────────────────────┐ ┌──────────────┐ ┌─────────────────────────┐ │ Draws glyphs, sends │ WS │ Forwards raw │ attach│ tmux → bash │ │ keys as byte stream │◄─────►│ PTY bytes │◄─────►│ (PTY slave side) │ └─────────────────────┘ └──────────────┘ └─────────────────────────┘

Plain pipes (bash < file) would not work the same way: no TTY, no colors, broken interactivity. Forge always allocates a PTY for shell tabs via Docker’s exec API with Tty: true.

Interactive shell: the full streaming path

When you open or focus a shell tab, Forge opens a live pipe from that tmux window to xterm in your browser. Output is not polled — bytes arrive as the shell produces them.

Step 1 — Create a shell tab (HTTP)

  1. You click + in the terminal tab strip.
  2. The web UI calls POST /internal/terminal/tabs with your sessionId.
  3. The Forge server runs tmux new-window in your sandbox container and returns the new window name (tab id).
  4. The UI adds the tab immediately (optimistic update) while the server confirms.

Step 2 — Open a session WebSocket (browser → Forge server)

The terminal dock opens one WebSocket for the whole workbench session: 

ws://<tool-runner-host>/internal/terminal/session?sessionId=<id>

Shell tabs then subscribe to streams like shell:main. App and job tabs subscribe to app:… / job:… on the same connection.

Step 3 — Forge attaches to tmux via Docker (server → container)

The session router (terminalSession.ws.ts) does the following for a shell subscribe:

  1. Resolves your sessionId to a sandbox container name.
  2. Calls attachShellWindow, which runs Docker exec with a TTY:
tmux attach-session -d -t forge:<window>
  • -d — detach any other client attached to that session view (one attach at a time for this attach command).
  • -t forge:sh-a1b2c3 — target the specific tmux window (tab).

Under the hood Forge talks to the Docker Engine API over the socket (/var/run/docker.sock):

  1. POST /containers/{id}/exec — create exec with AttachStdin/Stdout/Stderr: true, Tty: true
  2. POST /exec/{id}/start with HTTP upgrade — hijack the stream
  3. Raw bytes on that socket are PTY I/O (not line-delimited JSON)

Step 4 — Output streaming (container → browser)

When bash (via tmux) writes to the terminal:

bash prints bytes ↓ tmux multiplexes the PTY for that window ↓ docker exec attach stream (PTY master) ↓ Forge server: encodeDataFrame(stream, chunk) → ws.send(binary) ↓ Browser: TerminalSessionClient demux → term.write(chunk) ↓ You see text, colors, cursor moves on screen

Chunks are opaque terminal bytes — ANSI escape sequences for color, cursor positioning, clearing lines, etc. xterm interprets them; Forge does not parse command output.

After attach succeeds, the server sends one JSON control message: {"type":"ready","stream":"shell:main"}. Data frames are binary with a stream header.

Step 5 — Input streaming (browser → container)

When you type in xterm:

Key press in xterm ↓ term.onData → encodeStdinFrame(stream, bytes) → ws.send ↓ Forge server: parseStdinFrame → attach.write(data) ↓ Docker hijacked stream → stdin of attach process ↓ tmux → bash readline / program stdin

Special keys (arrows, Ctrl+C, paste) are encoded as the same byte sequences a local terminal would send. Stdin is rejected for app:* / job:* streams.

Step 6 — Terminal resize

When you resize the dock or the split pane, xterm recalculates columns and rows and sends JSON:

{"type":"resize","stream":"shell:main","cols":120,"rows":32}

The server calls Docker’s POST /exec/{id}/resize?w=&h= so programs like vim or full-screen CLIs reflow correctly.

WebSocket protocol (session mux)

Connect once:

ws://127.0.0.1:4000/internal/terminal/session?sessionId=<id>
Direction Payload Meaning
Client → server {"type":"subscribe","stream":"shell:main"} Start attach for that stream
Client → server {"type":"unsubscribe","stream":"…"} Stop attach
Client → server Binary stdin frame / JSON resize Shell only
Server → client {"type":"ready","stream":"…"} Attach succeeded
Server → client Binary data frame (stream header + payload) PTY or log bytes
Server → client {"type":"exited","stream":"…"} App/job process ended

Default PTY size on attach: 80×24. After ready, the client fits xterm to the pane and sends the real dimensions.

Connect, disconnect, and refresh

The workbench opens one session WebSocket. Tabs subscribe / unsubscribe streams; collapsing the dock unsubscribes followers but the socket can stay for reconnect.

Event What happens What happens to bash / logs
Switch shell tab Unsubscribe old shell stream; subscribe new Both shells keep running in tmux
Dock open with apps/jobs Subscribe app/job streams even if not focused Boot output buffered in xterm while you stay on Shell
Collapse dock Unsubscribe streams (session client may reconnect later) Processes keep running
Refresh workbench New session WS; resubscribe visible tabs tmux + log files persist in the container
Close shell tab (×) Unsubscribe + tmux kill-window That shell ends
Close app/job tab (×) Unsubscribe + client-hide / unpin Process keeps running; app may reappear after reload if still running

Job and app tabs

Run apps and background agent jobs write stdout/stderr to files inside the container. New starts also echo a header line $ <command> into the log before process output: 

/tmp/forge-app-<sanitized-name>.log    ← preview_start / Run panel
/tmp/forge-term-<job-name>.log         ← run_terminal background:true

Apps appear in the vertical sidebar when running or when a log file already exists. Jobs are auto-subscribed when a background run_terminal appears in chat; they show in the composer strip and open in the dock from that strip (no Show in terminal CTA). Closing a job tab removes it from the dock only.

Follow streams use a single tail -n 500 -F Docker attach (replay + live). While the dock is open, app/job streams stay subscribed even if another tab is focused. While a process is running but no bytes yet, the pane shows Starting….

How the agent gets job output (not HTTP /terminal/logs)

  • Foreground run_terminal: command runs via dockerExec; stdout/stderr returned in the tool result and shown in chat.
  • Background: process appends to the log file; the tool returns an initial tail and tells the agent to poll with action=logs.
  • action=logs calls terminalJobLogs / readBackgroundJobLogs inside the server — it does not use HTTP GET /internal/terminal/logs (that route was removed as unused by the dock).
  • The UI follows the same files over the session WebSocket.

Tab metadata is polled every 8 seconds via GET /internal/terminal/tabs (shells + apps). Job pins are client-side. Log bytes use the session WebSocket only.

Why tmux?

  • Persistence — shells survive browser refresh and WebSocket disconnect.
  • Multiple tabs — one session, many windows; attach targets one window at a time.
  • Standard tooling — familiar model for anyone who uses remote dev boxes.

tmux does not provide a separate “streaming API.” Attaching is the stream — the same model as SSH or docker run -it.

FAQ

Does tmux “stream” output?

tmux holds PTY sessions. When you attach, you get a continuous byte stream — there is no separate log tail or poll. Streaming is a property of the PTY + attach pipe, not a tmux-specific network protocol.

Why WebSocket for shells and apps?

Shells need low-latency bidirectional I/O. App and job logs stream from container files over the same session WebSocket via tail -F. Foreground agent commands stay in chat; background jobs appear in the compose running strip via auto-subscribe and open in the dock from there.

Is my keystroke data stored?

Forge forwards PTY bytes between browser and container. Shell scrollback lives in tmux/xterm client memory; Forge does not persist terminal transcripts in this path unless other features (e.g. agent tools) explicitly capture command output.

What if tmux is missing in the image?

Shell tabs fail with a rebuild hint. Rebuild the sandbox image after pulling terminal changes (pnpm docker:sandbox or your project’s documented rebuild step).
